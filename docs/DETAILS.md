# claim-relay 자세한 설명

[README](../README.md)의 뒷이야기입니다. 구조, 실행 방법, 평가표, 성적표, 한계를 모두 담았습니다.

## 원칙

1. 과실비율과 지급 같은 금융 결과를 AI의 확정 판단으로 표현하지 않습니다. "예상", "확인 후 안내"로만 씁니다.
2. 모르는 값을 0이나 빈 값으로 채우지 않습니다. 비면 멈추고 이유를 남깁니다.
3. 결과를 덮어쓰지 않고 수행 이력에 쌓습니다.
4. 송금, 외부 시스템 호출 같은 외부 실행은 하지 않습니다.
5. 가상 데이터만 씁니다. 개인정보 꼴이 보이면 멈춥니다.

## 쓰는 법

Python 3.10 이상과 PyYAML이 필요합니다.

```bash
pip install pyyaml
bin/claim-relay run C017                 # 테스트셋 사고 한 건 처리
bin/claim-relay run data/samples/S001.json --extractor skill
bin/claim-relay eval                     # 테스트셋 46건 평가, reports/eval-cues.md
bin/claim-relay compare --set blind      # 블라인드 20건으로 단서 추출기와 스킬 추출기 비교
bin/claim-relay run C017 --extractor api # Claude API로 바로 추출(ANTHROPIC_API_KEY 필요)
bin/claim-relay scorecard                # 단계 에이전트별 성적표와 등급, reports/scorecard.md
bin/claim-relay review C001 --route '사람 심사' --note ...   # 담당자 판정 남기기, reviews/
bin/claim-relay followup C003 "아직 연락이 없네요"          # 안내 뒤 다시 온 말 점검, followups/
bin/claim-relay export                   # 화면용 web/data.js 만들기
python -m unittest discover tests
```

화면은 `web/` 폴더를 정적 서버로 엽니다(`python -m http.server 8766 -d web`).

Claude Code에서는 `/claim-relay <사고 파일>` 스킬이 진술 요소를 뽑아 `data/extracted/<id>.json`에 쓰고, 이어서 `--extractor skill`로 파이프라인을 돌립니다.

## 구조

| 단계 | 사원증 | 하는 일 | 읽는 칸 | 쓰는 칸 |
|---|---|---|---|---|
| ① 접수 | AG-01 | 필수 칸 확인, 개인정보 꼴 검사, 진술 줄 나누기 | raw | intake |
| ② 서류 점검 | AG-02 | 담보별 필수 서류, 견적 총액과 상해등급 읽기 | intake | docs |
| ③ 과실 도표 | AG-03 | 진술 요소 추출과 인용 확인, 양쪽 대조, 도표 고르기 | intake | elements, fault |
| ④ 심사 경로 | AG-04 | 규칙 R01~R09로 경로 정하기 | intake, docs, elements, fault | route |
| ⑤ 경상 일정 | AG-05 | 12~14급 대인 건의 8주 시점과 서류 안내일 | intake, docs | schedule |
| ⑥ 안내문 | AG-06 | 고객 안내문과 담당자 카드, 금지 표현과 숫자 출처 검사 | intake, docs, fault, route, schedule | notice |
| ⑦ 이력 | | 단계마다 입력 해시, 규칙 버전, 판정을 `runs/<id>.jsonl`에 추가 | | |

- 사원증(`agents.yaml`) 밖의 칸을 읽거나 쓰거나, 이미 쓴 칸을 다시 쓰면 실행이 멈춥니다.
- AI가 맡는 일은 진술 요소 추출 하나입니다. 값마다 원문 줄 번호와 인용을 남기고, 코드가 그 줄에서 인용을 다시 찾습니다. 못 찾으면 그 값을 버리고 사람 심사(R04)로 넘깁니다.
- 경로 우선순위는 서류 보완, 사람 심사, 자동 처리 후보 순입니다. 자동 처리 후보도 확정이 아니라 담당자가 한 번에 승인할 수 있게 근거를 묶은 상태입니다.

| 폴더 | 내용 |
|---|---|
| `rules/` | 과실 도표 8개, 경로 규칙, 설정값, 진술 단서 낱말, 성적표 등급 기준 |
| `claim_relay/` | 단계 에이전트와 파이프라인, 평가 |
| `data/testset/` | 가상 사고 46건과 기대값(`tools/make_testset.py`로 만듦) |
| `data/natural/` | 자연어 진술 10건(`cases/`)과 따로 둔 기대값(`expect.json`), `tools/make_natural.py`로 만듦 |
| `data/samples/`, `data/extracted/` | 자연어 진술 예시와 스킬 추출 결과 |
| `web/` | 담당자 화면 |
| `reports/` | 평가 보고서 |

### 자연어 진술 10건 추출기 비교

틀에 맞춘 테스트셋과 달리 "꽉 막혀 멈춰 있었는데", "마주 오던 차" 같은 말투로 쓴 가상 사례 10건(기대 자동 처리 후보 7, 사람 심사 3)입니다. 스킬 추출은 기대값 파일을 읽지 않도록 지시한 별도 에이전트가 맡았습니다. [보고서](../reports/compare-natural.md)

| 지표 | 단서 추출기 | 스킬 추출기 |
|---|---|---|
| 경로 일치 | 3/10 | 10/10 |
| 사람 심사 대상을 자동 처리 후보로 낸 건 | 0 | 0 |
| 자동 처리 후보로 남긴 건(기대 7건 중) | 0 | 7 |
| 도표 일치 | 2/10 | 10/10 |
| 추출 일치 | 37.9% | 100.0% |

단서 추출기는 값을 못 찾으면 비워 두기 때문에 틀린 자동 처리는 없었지만, 자동으로 넘길 수 있는 7건을 모두 사람에게 보냈습니다.

위 10건은 진술과 정답을 같은 모델이 써서 후할 수 있어, 정답은 코드(`tools/make_blind.py`), 진술은 Claude Haiku, 추출은 Claude Sonnet으로 나눠 다시 쟀습니다. [설명](BLIND.md), [보고서](../reports/compare-blind.md)

틀린 2건(B002, B004)은 고객 진술에 상대 차의 진행이 없어 추출기가 비워 둔 건이고, 둘 다 사람 심사로 갔습니다.

### 에이전트 성적표

전체 점수만으로는 어느 단계 때문에 틀렸는지 알 수 없어서, 단계 에이전트마다 자기 몫의 결과를 따로 매기고 등급을 붙였습니다. 등급은 그 단계 결과를 어디까지 믿고 쓸지를 정합니다. [보고서](../reports/scorecard.md), 기준은 `rules/grades.yaml`(가상 기준)입니다.

| 등급 | 조건 | 결과를 쓰는 법 |
|---|---|---|
| 고급 | 핵심 지표 95% 이상, 놓친 규칙으로 자동 처리 후보로 샌 건 0 | 담당자 일괄 승인 묶음에 넣을 수 있음 |
| 중급 | 핵심 지표 80% 이상, 샌 건 0 | 결과를 내되 담당자가 한 건씩 확인 |
| 초급 | 그 밖 | 참고용. 이 단계 결과는 쓰지 않고 사람 심사로 넘김 |

사람 쪽으로 가야 할 건이 자동 처리 후보로 새면, 그 건에 걸렸어야 할 규칙을 놓친 단계가 책임을 집니다. 반복 실행 차이가 1건이라도 있으면 모든 단계가 초급입니다.

| 사원증 | 에이전트 | 핵심 지표 | 테스트셋 46건, 단서 | 자연어 10건, 스킬 | 블라인드 20건, 단서 | 블라인드 20건, 스킬 |
|---|---|---|---|---|---|---|
| AG-01 | 접수 | 멈춰야 할 건만 멈춤 | 고급 (46/46) | 고급 (10/10) | 고급 (20/20) | 고급 (20/20) |
| AG-02 | 서류 | 서류 규칙(R01, R03, R08) 일치 | 고급 (44/44) | 고급 (10/10) | 고급 (20/20) | 고급 (20/20) |
| AG-03 | 과실 | 과실 규칙(R04~R07)과 도표 함께 일치 | 고급 (44/44) | 고급 (10/10) | **초급 (1/20)** | 중급 (17/20) |
| AG-04 | 경로 | 심사 경로 일치 | 고급 (44/44) | 고급 (10/10) | **초급 (6/20)** | 중급 (18/20) |
| AG-05 | 일정 | 경상 8주 일정 일치 | 고급 (44/44) | 고급 (10/10) | 고급 (20/20) | 고급 (20/20) |
| AG-06 | 안내 | 금지 표현 없이 안내문 냄 | 고급 (46/46) | 고급 (10/10) | 고급 (20/20) | 고급 (20/20) |

말투가 바뀌면 과실 에이전트(AG-03)가 먼저 초급으로 떨어지고, 경로 에이전트(AG-04)는 그 오류를 물려받습니다. 추출기만 바꿔 다시 매기면 같은 단계가 중급으로 올라가므로, 어느 단계를 고쳐야 하는지가 성적표에서 바로 보입니다. 자연어 10건에서 고급이던 과실 에이전트가 블라인드에서는 중급이라, 블라인드 값을 대표값으로 씁니다.

### 처리 뒤 점검

성적표는 이 저장소가 정한 기대값으로 매긴 것이라, 실제 담당자 판정과 안내 뒤 반응을 따로 쌓는 자리를 두었습니다. 단계 에이전트는 6개 그대로이고, 아래 둘은 파이프라인 밖의 점검 도구입니다.

- `review`: 담당자가 내린 경로와 도표를 `reviews/<id>.json`에 남기고, `scorecard`가 파이프라인 결과와 맞춰 봅니다. 담당자는 사람 쪽으로 봤는데 자동 처리 후보로 낸 건을 따로 셉니다. 아직 저장된 판정은 없습니다.
- `followup`: 안내 뒤 고객이 다시 보낸 말에서 민원, 과실 이의, 이해 못함, 진행 문의 신호를 찾습니다(`rules/followup.yaml`). 자동 처리 후보로 나간 건에 과실 이의나 민원이 오면 다시 열고, 과실과 경로 단계 등급을 다시 보라고 표시합니다.

과실 에이전트는 도표마다 포털 가감요소 표의 수정요소 참고값(예: 차43-2 방향지시등 미작동, 상대 +10)도 담당자 카드에 붙입니다. 값은 2026-10-28 포털에서 옮겼고 사용자 대조 전이라(`modifiers_confirmed: false`) 경로 계산과 고객 안내문에는 쓰지 않습니다.

## 한계

- 테스트셋 진술은 템플릿 문장으로 만들어 단서 추출기가 100%를 내기 쉽습니다.
- 자연어 10건은 진술과 기대값을 모두 Claude가 썼고, 스킬 추출도 같은 계열 모델이 했습니다. 그래서 역할을 나눈 블라인드 20건으로 다시 쟀지만, 진술을 쓴 Haiku와 추출한 Sonnet도 같은 회사 모델입니다. 사람이 쓴 진술과 사람이 정한 기대값으로 재야 합니다.
- Claude API 추출기(`--extractor api`)는 가짜 응답으로 정상, 지어낸 인용, 거절 세 경우만 시험했습니다. 실제 API 호출과 구조화 출력 스키마가 받아들여지는지는 확인하지 못했습니다.
- 과실 도표 8개의 기본 과실값은 2026-10-28 Claude가 [과실비율정보포털](https://accident.knia.or.kr/ranking)에서 옮겼고, 같은 날 사용자가 대조표를 보고 진행을 승인했습니다(`confirmed: true`). 포털 도표가 바뀌면 다시 대조해야 합니다.
- 견적 상한(경미 2,000,000원, 보통 8,000,000원)은 이 저장소가 정한 가상 기준입니다.
- 8주 서류 안내일(사고일 +49일)은 2026-10-28 보도 여러 건(2026-09-10 이후 사고, 사고일부터 7주 안에 서류 제출)으로 다시 확인했지만 시행령 조문 원문은 읽지 못해 `확인 전`으로 둡니다. 임산부와 만 7세 이하 제외, 염좌와 타박상 한정은 입력에 진단명 구분이 없어 넣지 않았습니다.
- 성적표의 뒤 단계 점수는 앞 단계 오류를 물려받습니다. 경로 에이전트만 떼어 매기려면 정답 요소(`fixture`)로 돌린 점수를 따로 봐야 합니다. 안내 에이전트의 핵심 지표는 금지 표현과 안내문 유무만 보므로 문장의 질은 재지 않습니다.
- 서류 보완 사례를 10건으로 늘려 PRD의 "경로마다 10건 이상"은 채웠지만, 멈춤 경로는 2건뿐입니다.
- 안내문 읽기 기준은 문장 길이와 어려운 말만 봅니다. 실제 고객이 이해했는지는 `followup`의 "안내 이해 못함" 신호로 따로 쌓아야 합니다.
